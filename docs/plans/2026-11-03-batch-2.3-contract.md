# Batch 2.3 — Settings split: the contract

**Written:** 3 November 2026, before any code, from the plan
(`2026-10-30-phase-2-frame.md`, *Batch 2.3* and *Choices* 3, 4, 9, 10, all
approved with the recommendation on 30 October) and frame 6 of
`docs/design/hba-os-shell-2026-10-25.html`. Backend and frontend are built in
parallel against this; a change to it is made here first.

"The owner" below means whoever holds `settings.manage` (the `admin` role).

## 1. Addresses and who sees them

| Address | Who | What |
|---|---|---|
| `/settings` | anyone who may open Settings | goes on to `/settings/me` (or an old `?section=` link's new home, §5) |
| `/settings/me` | **every member of staff** (any staff permission; never a model) | Theme, two-step sign-in, *Signed in on*, email preferences — today's *My preferences* panels, unchanged |
| `/settings/team` | owner | today's Team section (roster, invite, pending invitations) unchanged; Batch 2.4 redraws it |
| `/settings/integrations` | owner | frame 6 (§3) |
| `/settings/company` | owner | Pay policy, go-live month (read-only line), the whole activity log |
| `/affiliates/brand-codes` | `affiliates.view` | today's Brand codes panel; off the sidebar, linked from Models, counted as Models' section |
| `/affiliates/historical` | `compensation.manage` | today's Historical setup panel (and its "History is complete" line); off the sidebar, linked from Payments while months are open, counted as Payments' section |
| `/affiliates/activity` | `audit.view` | the activity log narrowed to Affiliates' entries (§4); off the sidebar, linked from Overview, counted as Overview's section |

- The sidebar's Settings entry opens `/settings/me` and shows to every member
  of staff (`canOpenSettings` becomes "holds any staff permission"). Its
  sections are drawn as the mockup's sidebar draws them: Me; Team and access,
  Integrations, Company for the owner only.
- Somebody without the owner's permission who opens `/settings/team`,
  `/integrations` or `/company` gets the frame's "not yours" page, as other
  refused addresses do today. The server refuses the reads in any case.
- The read-only *Connection* panel others saw under "Shopify and sync" goes
  (Today already shows a broken Shopify).
- **Staff invitations become the owner's (Choice 4).** The Team page is the
  owner's, so the server refuses the affiliate manager's staff invitations
  too: `POST /api/auth/invitations` naming a **staff** role, and
  `POST /api/staff/invitations/{id}/resend` and `…/{id}/revoke` on a staff
  invitation, require `settings.manage` ("Permission required:
  settings.manage"). **Model invitations are unchanged**
  (`invitations.send`, Affiliates → Models → Invite, which resends and
  withdraws through the same two routes). The affiliate manager keeps
  `invitations.send`. `GET /api/staff/invitations` (the affiliate
  manager's own list, Settings audit X2) is **retired**, not gated: nothing
  called it once the Team page became the owner's, whose roster
  (`GET /api/staff`) carries the pending invitations.

## 2. Session (no change of shape)

The frontend decides from `session.permissions` (`settings.manage`,
`audit.view`, `compensation.manage`, `affiliates.view`) — no new session
field.

## 3. `GET /api/integrations` (owner only; 403 otherwise)

Built from what each department already records; **no new outside call**.
Departments are reached only through their `public.py` (a new import-linter
contract for `app.shared.api.integrations` and its service, as Today's).
A source that cannot be read leaves its row with `state: "unknown"` and is
logged, never a made-up figure; the other rows stay.

```jsonc
{
  "checked_at": "2026-11-03T14:22:05+00:00",      // when this answer was built
  "connections": [
    {
      "key": "bosta",                  // shopify | whatsapp | bosta | estebdal | email | storage
      "name": "Bosta",
      "what": "Deliveries",            // the mockup's small line under the name
      "used_by": "Used by Operations and order pages",
      "state": "failed",               // working | late | failed | not_connected | never | unknown
      "why": "Bosta refused the key at 09:40. Paste a new key from Bosta's dashboard.",  // only when failed / late / not_connected; null otherwise
      "when_label": "Last read",       // "Read at" / "Last read" / "Last message" / "Last sent" / "Last file stored"
      "when": "2026-11-03T09:38:00+00:00",   // the last time it worked (last clean read / message / email sent / file kept), failed or not; null when there is none
      "key_form": "bosta"              // which existing key form "Replace key"/"Details" opens; null when the key lives in Railway (email, storage)
    }
  ]
}
```

Order and words, as frame 6 draws them (the order is fixed; failed rows are
not moved):

| key | name | what | used_by | when_label | state from |
|---|---|---|---|---|---|
| `bosta` | Bosta | Deliveries | Used by Operations and order pages | Last read | Operations freshness (`describe`): fresh→working, stale→late, failed→failed, not_connected, never; `when` = last clean read; `why` = the recorded error |
| `shopify` | Shopify | Orders, products and tags | Used by Operations, Affiliates and Inbox | Read at | Operations freshness for `shopify`, same mapping; `key_form: "shopify"` |
| `whatsapp` | WhatsApp | Customer chats and confirmations | Used by Inbox | Last message | Inbox connection (`describe_whatsapp`): no row → not_connected; row but keys unreadable → failed with its `problem`; else working; `when` = latest message in or out |
| `estebdal` | E-stebdal | Returns and exchanges | Used by Operations | Read at | as Bosta |
| `email` | Email | Invitations, password resets, model emails | Used by everyone | Last sent | Notification outbox: no mail transport configured → not_connected; the mail **service's own** latest failure newer than the last email sent → failed; else working; nothing ever sent → never. A service failure is read from the error the outbox records (`SERVICE_FAILURES` in `app/shared/services/integrations.py`): the account's sign-in refused, STARTTLS refused, the key refused (401/403), the sender domain not verified (a 4xx saying so), rate-limited (429), the provider unreachable or failing (5xx) or the SMTP connection failing after every retry. An email's own refusal (no address, an expired code, one address refused) never counts. `when` = the last email sent (null if none), failed or not; `why` says what and when, e.g. "The mail service refused the key at 09:40." |
| `storage` | File storage | Chat photos and voice notes | Used by Inbox | Last file stored | no bucket configured → not_connected; **the bucket** refused the latest file whose copy into it finished → failed; else working; none kept yet → never. A file failed because it was too large or WhatsApp would not hand it over is not storage failing and is passed over: the Inbox notes the bucket's own refusal on the file's message (`extra.copy_refused_at`, written where a `StorageError` is caught; no migration). `when` = the last file kept (null if none), failed or not; `why` = "File storage refused the latest file at 09:40." **No "GB stored"** (Choice 9: not readable without a new outside call) |

**`when` on a failed row** is the last time the connection worked, as
Bosta's is its last good read; when the failure happened is said in `why`,
in Cairo time (`at_words`: "at 09:40", "yesterday at 09:40", "on 26 Oct").

**Departs from frame 6 (3 November):** File storage reads "Chat photos and
voice notes · Used by Inbox", not "…receipts · Used by Inbox and
Affiliates": only the Inbox's files go to the bucket (models' proofs are
kept in the database), and the row should not claim what it does not
watch. Email turns to *Not working* only on a failure of the mail service
itself, not one email's own problem (no address, an expired code).

The pill words: working "Working", late "Late", failed "Not working",
not_connected "Not connected", never "Not read yet", unknown "Could not
check".

The page head says "N connections · M is/are not working" (M counts
`failed`, plus `late` and `unknown`; omitted when 0) and "Checked …" from
`checked_at`.

**Key forms (Choice 10).** `Replace key` (failed rows) and `Details` (the
others) open, for that row, the **existing** component that today changes
that key: Shopify's from the old *Shopify and sync* section (`DataPanel`),
Bosta's and E-stebdal's and WhatsApp's from their Operations / Inbox
screens. The Operations and Inbox screens keep theirs unchanged. Email and
File storage open a short *Details* with the row's facts and the line "This
key is set on the server, not here." No new key endpoint.

## 4. The activity log by department

`GET /api/audit` and `GET /api/audit/filters` keep their shapes. What they
return depends on the reader:

- **The owner** (`settings.manage`): everything, as today, including entries
  with no department (sign-ins, staff access, Settings, connections).
- **Anyone else with `audit.view`**: only entries whose `department` is one
  they hold — held exactly as Today decides it: `inbox.use` → `inbox`,
  `order_ops.view` → `operations`, `affiliates.view` → `affiliates`. Entries
  with no department are never theirs. An entry written before the column
  existed (stored department empty) counts as the department its action
  names (`department_of`), worked out when it is read — the row itself is
  never rewritten — so nobody loses the history they read today. A **model's
  invitation** (`invitation.*` whose `after.role` is `affiliate`, or an
  acceptance whose `after.roles` is exactly `["affiliate"]`) is read as
  `affiliates` the same way; staff invitations and sign-ins stay the
  owner's (ADR 0067, decision 7). `include_sign_ins` changes nothing for
  them (sign-ins have none), so the page offers it to the owner only.
- `/filters` for them lists only the **people** who appear in the entries
  they may read, and only the **kinds** those entries can hold (for
  somebody holding Affiliates alone: `money`, `access`, `models`,
  `content`, `settings` — `inbox` and `operations` go); `models` stays the
  roster (they already see every model).
- New optional query `department=<name>`, on both `/api/audit` and
  `/api/audit/filters`: narrows further to one department, for the owner
  too (must be one the reader may read, else 403; unknown, 422). The
  Affiliates activity page sends `department=affiliates`; Company sends
  nothing.

## 5. Old links

Every `/settings?section=…` link lands on its new home (the frontend redirects
with `replace`; other query keys are kept):

| `section=` | goes to |
|---|---|
| `team` | `/settings/team` (non-owner: `/settings/me`) |
| `shopify` | `/settings/integrations` (non-owner: `/settings/me`) |
| `historical` | `/affiliates/historical` |
| `codes` | `/affiliates/brand-codes` |
| `policy` | `/settings/company` |
| `activity` | owner: `/settings/company`; others: `/affiliates/activity` (keeping `q`, `affiliate_id`, …) |
| `advanced` | as `policy` |
| `appearance`, none, unknown | `/settings/me` |

Every link inside the app that builds `/settings?section=` is changed to the
new address.

**Links the server builds** (the Affiliates Overview notices,
`GET /api/operations/attention`) point at the new homes too: go-live month
unset → `/settings/company`; no mail, failed emails, failed order syncing →
`/settings/integrations`; discount codes nobody owns →
`/affiliates/brand-codes`. Settings' pages are the owner's, so for anybody
else those notices carry `where: null` and `action: null` (no button) and
their detail ends "The owner fixes this in Settings."; the Brand codes one
keeps its link.
